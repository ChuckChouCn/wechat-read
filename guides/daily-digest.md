# 微信日报（全部会话）

扫描**全部会话**的消息，按话题类型整理成简报。用户说「总结今天微信」
「微信日报」「今天有什么重要的」「今天谁找我了」时走这条路。

> 用户点名了单个会话 → 用 `summarize-chat.md`。
>
> **命令参数不确定就跑 `wechat-read summarize --help`**，或看
> `commands.md`。**不要去读 `cli.py` 源码** —— 用法信息本文档加上
> `--help` 已经给全了。

## 核心原则：深度挖掘，别浅尝辄止

用户的预期是「今天微信里有什么值得我知道的」，**不是把所有消息搬一遍**，
但更**不是只挑三五条最显眼的**。

**目标产出 15-40 个话题。** 一天几百上千条消息里，值得记录的信息远不止
三五个。如果你只挖出 5 个，通常是挖得不够深。

**该挖的东西**（别只抓最显眼的）：

- 讨论（大家在聊什么、谁说了什么观点）
- 提问（谁在问什么、得到的回答是什么）
- 资源（分享的链接、工具、文章、教程）
- 经验（踩坑、心得、方法论）
- 事实（时间、地点、价格、规则、数字）
- 观点（金句、判断、看法）
- 动态（人员变动、约见、合作、发布）

**只有这些才该丢**：纯表情、纯符号、"哈哈""收到""好的"、无意义刷屏。

## 重要：谁来推理

本流程**不调用任何 LLM**。推理由**你（宿主 Agent）**完成：

```
你（Agent） → 读本文件 → 调 CLI 取输入包 → 你自己挖掘归纳 → 调 CLI 渲染
```

项目不绑定任何 LLM SDK，也不需要额外 API Key。**你自己就是模型。**

## 数据完整性铁律（零丢失原则）

**这是最重要的一条，优先于其他所有考虑。**

1. **时间范围是闭区间**：说"今天"就必须覆盖 `00:00:00 ~ 23:59:59`，
   不能只取"最近 N 条"。日报是**区间聚合**，不是聊天翻页 ——
   翻页看最近的 500 条没问题，但做日报会直接把早晨的消息淹掉。

2. **禁止用条数截断代替时间范围**。`summarize` 走的是区间闭包语义，
   范围内一条不落 —— 这正是它存在的理由。放心读全量。

3. **降噪不等于丢弃**。低信息量消息会被标记 `low_value` 并默认过滤，
   但 `excluded_low_value` 会报告过滤了多少条，不是静默丢弃。

4. **必须核对对账指标**。输入包里的 `audit` 字段是零丢失的证据：

```json
"audit": {
  "sql_total": 1949,      // 数据库里该范围的真实条数
  "fetched": 1949,        // 实际取到的
  "kept": 1949,           // 交给模型处理的
  "loss": 0,              // 丢失条数 —— 必须为 0
  "earliest_time": "2026-09-29 00:03:54",
  "latest_time": "2026-09-29 19:02:30",
  "coverage": "完整",
  "zero_loss": true
}
```

**开工前先看 `loss`**：不为 0 说明数据有问题，先解决再总结，
不要基于残缺数据出结论。`coverage` 不是"完整"时，多半是该时段确实
没人说话（正常），但如果 `earliest_time` 明显晚于范围起点且该群当天
很活跃，要警觉。

## 四条铁律

1. **筛选，不罗列**。挑出真正值得知道的，丢弃噪声。
2. **跨会话归纳**。同一件事在多个群出现时合并成一条。
3. **可溯源**。每条带 `chat`（来自哪个会话）+ `source_message_ids`，
   **只能引用输入包里真实存在的 id**。
4. **不要判断重要性**。不要分「重点」和「其他」，也不要写待办、
   需要回复这类推断 —— 那是主观判断，容易出错。
   你只做两件事：**把内容挖全**，**按类型归类**。哪条对读者有用，
   让读者自己判断。

## 第 1 步：取输入包

**用 `--output` 直接写文件，不要用 shell 的 `>` 重定向。**

```bat
rem 默认今天
wechat-read summarize --output pack.json

rem 指定范围
wechat-read summarize --since 2026-09-28 --until 2026-09-29 --output pack.json
```

> ⚠️ **为什么必须用 `--output` 而不是 `>`：** 日报的输入包可能几 MB，
> 要落盘才能读。而 PowerShell 的 `>` 不可控 —— **5.1 写 UTF-16、
> 7.x 写带 BOM 的 UTF-8**，都会让后续读取报编码错，逼你额外写一个
> "清洗编码"的脚本。`--output` 由程序自己写标准 UTF-8，没有这个环节。

> **不带 `chat` 参数**就是日报。带了 `chat` 会走会话摘要。

返回结构：

```json
{
  "kind": "daily_digest_input",
  "range": {"since": "2026-09-29", "until": "2026-09-29"},
  "chats": [{
    "username": "12345678901@chatroom",
    "display_name": "示例交流群A",
    "is_group": true,
    "message_count": 100,
    "excluded_low_value": 9,
    "messages": [
      {"id": "12345678901@chatroom:2985", "time": "...", "sender": "用户甲",
       "type": "text", "content": "...", "low_value": false, "reply_signal": false}
    ],
    "reply_signals": ["12345678901@chatroom:2990"]
  }],
  "stats": {"message_count": 299, "low_value_count": 36, "top_senders": [...]},
  "incremental": {"enabled": true, "chats_with_updates": 7,
                  "chats_reused_from_cache": 3},
  "instructions": {...}
}
```

> `chats[].messages[]` 已过滤低信息量；`reply_signals` 是**可能**需要回应的
> 消息 id 列表（规则匹配的结果，供你参考，不是最终判断）。
> `instructions` 内嵌了同样的规则，包是自描述的。

## 第 2 步：你来做挖掘归纳

按下面 schema 产出 JSON：

```json
{
  "kind": "daily_digest",
  "range": {"since": "2026-09-29", "until": "2026-09-29"},
  "overview": "两三句话概括今天微信的整体情况",
  "topics": [{
    "title": "短标题（一句话说清这件事）",
    "category": "领域分类",
    "chat": "来自哪个会话（显示名）",
    "summary": "一到两句展开说明",
    "key_points": ["具体要点，可省略"],
    "participants": ["涉及的人，可省略"],
    "source_message_ids": ["12345678901@chatroom:2985"]
  }],
  "chats": [{"username": "...", "display_name": "...", "message_count": 100}],
  "stats": {"message_count": 299, "low_value_count": 36}
}
```

### 话题的边界（关键）

**一个话题必须来自一段连续对话，时间跨度不超过 40 分钟。**

聊天是流动的：上午聊 A、下午聊 B，即使都关于「AI 工具」也是两个不同的
话题，要分开写。判断依据是**对话的连贯性** —— 如果中间隔了几小时、
或者话题已经转到别的事情上，那就是新话题。

引用消息时只引用这一小段里的，不要把一天的消息混进一个话题。

### 分类规则

**按「聊的是哪个领域/主题」分类，不是按内容形式。**

```
对：AI 工具、自媒体运营、大模型、创业变现、社群运营
错：讨论、提问、资源、经验、观点（这些是形式，不是领域）
```

**一份日报只分 3-6 个类，通常 3-4 个就够。**
分类名由你根据当天实际聊的内容归纳，用简短中文（2-6 字）。
同一领域的话题必须归到同一个类；不要为一个话题单开一类。

## 第 3 步：交付

**默认：直接在聊天框回答。不要生成 HTML 文件。**

「总结今天微信」是**问**，不是**要文件**。哪怕它叫"日报"，
默认也是在对话里把内容说出来：

```
今天 8 个会话 299 条消息，主要三件事：

【AI 工具】
· 平台对大模型知识工作者的冲击讨论 —— 集中在……
· 有人分享了三个提效工具，群里两人当天就试了

【自媒体运营】
· B 站新号入驻扶持计划开始报名，门槛是近三月发作品 ≤4 篇、粉丝 <1w
```

**但结论 JSON 仍然要写** —— 它是缓存所需的中间产物，写它 + 跑一次校验，
下次才只需处理新消息：

```bat
wechat-read render 日报.json --verify-against pack.json --format json
```

`--format json` + 不带 `--output` 就只做校验和存缓存，不产生任何文件。

**一定要带 `--verify-against`** —— 它做三件事：

1. **校验溯源** —— 丢弃你编造的 `source_message_ids`
2. **保存摘要** —— 把这次的结论存进缓存，下次只需处理新消息
3. **内联原文** —— 用户真要 HTML 时可点击任意结论回溯原文

若丢弃了 id，stderr 会提示条数 —— 说明你引用了不存在的消息，
**应修正结论而不是忽略**。

### 可选：用户要文件时才渲染

**只有用户明说了**「存成网页」「生成 HTML 日报」「导出」「保存成文件」，
才加 `--output` 产出文件：

```bat
wechat-read render 日报.json --verify-against pack.json --format html --output 日报.html
```

| 格式 | 用途 |
|---|---|
| `json` | 只校验+存缓存，不产文件（**默认路径用它**） |
| `text` | 紧凑文本，Agent 可读 |
| `markdown` | 带 checkbox 的文档 |
| `html` | 单文件网页，自带样式（用户要网页时才用） |

## 关于增量（避免重复分析）

日报的输入是**增量**的：已经总结过、且没有新消息的会话不会重复出现
在 `chats[]` 里，而是放在 `cached_summaries[]` 直接复用。

- `chats[]`：有新消息的会话。**读完其中的 messages[]，一条不要跳过。**
- `cached_summaries[]`：已总结过、无新内容的。**直接采信，不要重新分析。**
- `chats[].previous_summary`：该会话已有的结论，在其基础上补充新消息即可。

**不要因为消息数字大就自行截断或抽样。** 那是"需要你处理的新消息数"，
不是"上限"。全量读完再总结。

参数：

- `--rebuild` —— 忽略游标，从头重算（换账号、或怀疑缓存失效时用）
- `--no-cache` —— 完全不用缓存，每次全量处理

> **第一次跑**：还没有任何缓存，所以会全量处理，耗时较长。
> 从第二次起，只有新消息需要处理，会快很多。
> 渲染带 `--verify-against` 时才会写入缓存 —— 这是增量生效的前提。

## 规则

**必须**

- 筛选而非罗列；低信息量内容不进结论
- 每条带 `chat` + `source_message_ids`，id 真实存在
- 跨会话合并同一件事
- 用中文输出

**禁止**

- 输出所有消息
- 编造 `source_message_ids`
- 分「重点/其他」或写待办、需要回复这类主观判断
- 把一天的消息混进一个话题

## 完整示例

```bat
rem 1. 取今天全部会话的输入包（直接写 UTF-8 文件，不要用 > 重定向）
wechat-read summarize --output pack.json

rem 2. 你是模型 —— 直接读 pack.json，挖掘归纳，产出 日报.json
rem    （用你的写文件能力直接写，不要写脚本去 dump 消息或构造 JSON）

rem 3. 校验+存缓存（不产文件），然后在聊天框把日报内容回答给用户
wechat-read render 日报.json --verify-against pack.json --format json
```

> **三步就够，不需要任何过渡脚本。** 如果你发现自己在写
> "清洗编码""导出消息文本""构造合法 JSON" 这类辅助脚本，
> 说明某一步用错了 —— 多半是第 1 步用了 `>` 而不是 `--output`。
>
> 用户只是问「今天微信有什么」，就在聊天框里答。
> **只有用户说要网页/文件时**，第 3 步才改成
> `--format html --output 日报.html`。

聊天框里回答的形态：

```
═══ 微信日报 ═══
2026-09-29 ~ 2026-09-29
8 个会话 · 299 条消息（低信息量 36 条已弱化）

今天主要在几个 AI 社群讨论内容变现与平台规则，另有 B 站扶持计划的报名信息。

── AI 工具（3）──
· 平台对大模型知识工作者的冲击讨论
  讨论集中在…
  ← 45678901234@chatroom:1204 +2
```

## 失败处理

| 情况 | 表现 | 怎么办 |
|---|---|---|
| 范围内无消息 | `NO_MESSAGE_DB` | 换时间范围 |
| 密钥缺失 | `KEYS_MISSING` | 读 `setup.md` |
| 解密失败 | `DB_DECRYPT_FAILED` | `init --force` |
